## 목적

이슈 → 코드 분석 → 브랜치 → 계획까지 한 번에. 인자는 이슈 번호 (예: `71`, `#71`). 없으면 묻는다.

## 절차

1. **이슈 읽기.** `gh api repos/hyung6370/Dozy-AI/issues/<N>` 로 본문·마일스톤·라벨·댓글을 읽는다 (`gh issue view` 가 빈 출력을 내는 경우가 있어 api 를 쓴다). 작성 시점 이후 바뀐 전제가 있는지 확인한다 — 예: "AI 가 요약 외엔 안 쓰임" 같은 현황 문장은 지금 코드와 대조.
2. **코드 분석.** 본문이 언급한 파일·타입을 전부 열어 실제 시그니처를 확인한다. 추가로 다음을 반드시 본다.
   - 연결 지점: `DependencyContainer`, `Dozy_AIApp`/`AppDelegate`(훅·BGTask), `HomeViewModel.loadTodayData`(캐시 쓰기), `SettingsView`(설정 토글 위치)
   - 재사용 가능한 기존 패턴: 같은 종류의 서비스·유스케이스·순수 계산 enum 이 이미 있는지
   - 플랫폼 제약: 포그라운드 전용 API, 익스텐션에서 불가한 호출, 위젯 배포 타깃(iOS 26.0)
   - 어느 타깃에 넣을 파일인지 (CLAUDE.md "타깃 배치 기준")
3. **범위 점검.** 이슈 작업 항목 중 현재 인프라로 불가능하거나 다른 이슈 규모인 것이 있으면 구현 전에 말한다. 사용자가 범위를 줄이기로 하면 이슈 본문을 먼저 고친다 (`gh issue edit --body-file`).
4. **브랜치.** `git status` 가 깨끗한지 확인 → `dev` 최신화(`git fetch`, 필요 시 `git pull`) → `git checkout -b feat/<kebab-case>` (버그면 `fix/`). 이름은 이슈 제목의 핵심어 2~3개.
5. **계획 제시.** 만들 파일(경로 + 타깃), 고칠 파일(무엇을), 테스트 클래스와 케이스, 검증 명령을 표나 목록으로. 사용자가 "시작하자"고 이미 말했으면 계획을 보여 준 뒤 바로 구현에 들어간다.

## 구현 중 지킬 것

- 순수 계산을 먼저 분리하고 그것부터 테스트를 쓴다.
- 새 파일은 `project.pbxproj` 등록까지 해야 빌드된다 (xcodeproj gem, CLAUDE.md 참고). 등록 후 `git diff --stat` 으로 pbxproj 변경이 추가 위주인지 확인.
- 사용자 문구는 xcstrings 에 en 번역을 텍스트로 덧붙인다.
- 구현이 끝나면 `/verify` 로 빌드·테스트를 돌리고, 이슈 체크박스를 갱신하며 `## 구현 메모` 를 덧붙인다.
- 커밋은 사용자가 요청할 때만. 저작권 표시는 넣지 않는다.
