## 목적

대화에서 합의된 기능·버그·분석 결과를 Dozy 이슈 형식으로 옮겨 `gh issue create` 로 등록한다. 인자로 제목이나 한 줄 설명이 올 수 있다. 없으면 직전 대화 내용을 이슈 대상으로 본다.

## 절차

1. **코드 근거 확보.** 본문에 적을 파일·타입 이름은 반드시 저장소에서 확인한다 (`grep`, `ls`). 존재하지 않는 타입을 "재사용"으로 적지 않는다. 분석이 이미 대화에 있으면 재조사하지 않는다.
2. **마일스톤·라벨 확인.** `gh api repos/hyung6370/Dozy-AI/milestones --jq '.[] | "\(.number) \(.title) \(.state)"'` 와 `gh label list` 로 현재 값을 읽는다. 마일스톤은 사용자가 지정하지 않았으면 열린 것 중 로드맵상 맞는 것을 고르고, 애매하면 본문 작성 후 한 번만 묻는다. 라벨 기본값은 `enhancement`(기능) 또는 `bug`. 수익화 관련이면 `monetization` 추가.
3. **본문 작성.** 아래 템플릿을 스크래치패드 파일로 쓴 뒤 `gh issue create --body-file` 로 올린다. 한국어. 저작권·생성 도구 표시는 넣지 않는다.
4. **상호 참조.** 선행·후속 이슈가 있으면 `#번호` 로 연결하고, 분리 출처가 있으면 "참고"에 적는다. 생성 후 번호를 받으면 관련 이슈 본문의 플레이스홀더를 실제 번호로 갱신한다.
5. **결과 보고.** 이슈 URL, 마일스톤, 라벨, 핵심 작업 항목 3줄 이내.

## 템플릿

```markdown
## 배경
- 현재 상태(코드 근거: 파일·타입·줄 수)와 왜 지금 필요한지
- 관련 이슈·마일스톤 맥락

## 설계 원칙   ← 선택. 결정이 있을 때만
- 왜 이 구조인지 한 줄씩

## 작업 내용
### Domain
- [ ] `Domain/...` — 무엇을
### Data
- [ ] `Data/Services/...` — 무엇을
### Presentation
- [ ] 화면·설정·위젯 변경
### 그 외
- [ ] `DependencyContainer` 등록, `Logger.<category>`, Info.plist, 문자열 en 번역

## 설계 메모
- 트레이드오프, 플랫폼 제약, 대안을 택하지 않은 이유

## 범위 제외
- 이번에 안 하는 것과 그 이유, 후속 이슈 번호

## 검증
- [ ] iOS / macOS 빌드 통과
- [ ] 단위 테스트: 어떤 클래스에 어떤 케이스
- [ ] 시뮬레이터 / 실기기 확인 항목 (구체적 시나리오)

## 참고
- Console 필터 `subsystem:com.dozy-ai.Dozy-AI category:<Category>`
- 외부 문서 링크, 원안 요약
```

## 주의

- 작업 항목은 "무엇을 어디에"가 보이게 쓴다. "구현한다"만 있는 항목은 없앤다.
- 플랫폼 제약(포그라운드 전용 API, 익스텐션 제한, 배포 타깃)이 범위에 영향을 주면 "설계 원칙" 또는 "범위 제외"에 근거와 함께 적는다.
- 수익화 마일스톤(v2.0.4) 이슈면 Pro 게이팅(#92)·페이월(#93)과의 연결점을 한 줄 적는다.
